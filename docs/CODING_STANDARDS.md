# 编码与验证规范 · 同手写，同手验

> 适用范围：写代码、改代码、写文档、画图、报数字。
> 一句话：**每写一段东西，同时写它"怎么才算对"的判据；判据跑不出结果的，不算写完。**
>
> **agent 内置版**：这份规范随仓库发布为技能 `coding-standards`（见 `skills/coding-standards/SKILL.md`），
> 任何工作空间启动都能加载；其中机械可判的几档由 `verify` 工具真跑（语法 / 文档断链 / 文档代码块 compile / 跑测试）。
> 两版同源，改一份必须同步另一份 —— `tests/test_coding_standards.py` 会校验关键条款没有单边丢失。

这不是流程文档，是可检验的行为约定。每条规则后面都跟一个判据 —— 判据过不了，规则就等于没执行。

---

## 一、四条铁律

| # | 铁律 | 判据（做不到就是没遵守） | 违反的代价 |
|---|---|---|---|
| 1 | **没有验证输出的代码，不算写完** | 能贴出一条命令 + 它的真实输出 | "看起来对"的代码，错误会在三小时后以另一种形态出现 |
| 2 | **数字只能来自运行时或原始来源** | 每个数字都能补上"怎么得到的" | 文档说谎不会被报错，只会让人做错决策 |
| 3 | **一次只改一处，改完立刻验** | 本次 diff 只包含一个意图 | 改三处后失败，你不知道是谁干的 |
| 4 | **失败就重读，不猜着重试** | 同一命令不重复执行第 3 次 | 重试只是把同一个错误多犯几遍，还掩盖了原因 |

铁律 1 是本规范的全部：**测试不是 feature 之后的阶段，是 feature 的一部分。** 想不清楚"怎么验"通常意味着还没想清楚"要什么"。

---

## 二、验证分六档：知道该用哪一档

不同档位抓的错误**互不重叠**，所以"语法过了"永远不等于"逻辑对"。

| 档 | 手段 | 耗时 | 抓什么错 | 什么时候**必须**做 |
|---|---|---|---|---|
| 0 语法 | `verify(checks=["syntax"])`（内存 compile，不落 `__pycache__`） | 毫秒 | 拼写、缩进、未闭合括号、语法错误 | 每次保存 |
| 1 契约 | 断言注册数、函数签名、schema 字段 | 毫秒 | 注册漏了、参数改名、默认值丢了 | 动了注册/接口/配置 |
| 2 单元 | 纯函数直接喂输入断输出 | 秒 | 分支逻辑、边界处理 | 每次改逻辑 |
| 3 集成 | 起进程真跑一次（HTTP/CLI/文件） | 秒 | 接线错、路由错、序列化错 | 动了模块边界 |
| 4 端到端 | 连真实模型/外部服务跑一回合 | 分钟 | 模型侧行为、真实延迟、协议细节 | 动了提示词/描述/模型参数 |
| 5 视觉 | 渲染成图，`load_image` 逐张看 | 分钟 | 文字溢出、元素重叠、箭头指错、边缘裁切 | 产出任何图/版式 |

用法两条：

- **能用上一档解决的，不要动下一档。** 改一个纯函数的返回值，不需要起服务器。
- **该用下一档的，别只用上一档交差。** 改了工具描述却只跑语法检查 —— 语法永远是对的，因为描述本来就是字符串。

第 0 档最容易被跳过，也最便宜。写文档时也适用：**文档里的代码块同样要 compile**，不然读者抄走就报错（`verify(checks=["blocks"])` 就是干这个的）。

## 三、写 feature 时，同时写这三件

一个功能至少有三个场景要验。只写"正常路径"是半成品。

| 场景 | 断什么 | 反例（无效的测试） |
|---|---|---|
| 正常路径 | 输出内容对不对 | 只断"没抛异常" |
| **错误路径** | **错误文案里有没有指路** | 只断"抛了 ValueError" |
| 边界 | 空 / 超大 / 参差 / 编码 / 超时 | 只测了最理想的那一条 |

错误路径最常被测成废的。对照写法：

```python
# ❌ 只证明它会失败
with pytest.raises(ValueError):
    write_xlsx(p, '[["a","b"],["1"]]')

# ✅ 证明它失败时还在教模型/用户怎么改
try:
    write_xlsx(p, '[["a","b"],["1"]]')
except ValueError as e:
    msg = str(e)
    assert "缺的列用空字符串占位" in msg      # 有正解
    assert '[["列1","列2","列3"]' in msg      # 有可复制示例
```

为什么值得为一个断言多写两行：**错误文案是产品的一部分**。在 agent 里它是给模型的第二次指令；在人用的工具里它是给人看的下一步。写"失败"两个字，等于让调用方自己猜。

配套要求：**每个 feature 附一条可复制的验证命令**，写进 PR 或提交信息里。

```bash
python tests/test_tools.py          # 期望最后一行 PASS 且退出码 0
```

## 四、数字与事实：唯一可信来源是运行时

### 静态搜索会骗人

真实案例（就在这个仓库里）：

```bash
$ grep -c "@tool(" tools/*.py | ... | 求和
16

$ python -c "import tools; from agent.registry import all_specs; print(len(all_specs()))"
15
```

差的 1 个来自 `tools/__init__.py` 第 5 行的一句注释：`2. 用 @tool(name=..., description=..., parameters=...) 装饰处理函数`。

**结论：要断言"有多少个"，用运行时；要定位"改哪一行"，用 grep。** 这两件事经常被混着用。

同类陷阱：`grep -c "def test_"` 会数进被注释的用例；`wc -l` 会数进空行；"代码里没写死密钥"用 grep 断不出来（会漏 base64 和拼接）。

### 数字要能一键复现

文档里写一个数字，就得能在旁边给出得到它的命令。不能复现的数字，三个月后没人敢改。

```markdown
18 个工具、tools 数组 11359 字符 —— 复现：
python -c "import json,sys;sys.path.insert(0,'.');import tools;from agent.registry import all_specs;print(len(all_specs()), len(json.dumps(all_specs(),ensure_ascii=False)))"
```

### 估算必须标记为估算

本项目早期把"重写这套东西要多少行"估成 900 行，按代码块实测约 1500 行 —— 差了约 66%。估错了不影响开发，但会影响排期和他人的预期。

规矩：**没实测过的数字，写成"约 / 估"并注明依据；一旦要对外，先改成实测值。**

## 五、改动的纪律

| 规则 | 做法 | 为什么 |
|---|---|---|
| 先读后改 | 任何 `Edit` 之前先 `Read` 目标文件 | 凭记忆改文件 = 盲改；行号会漂，内容不会骗人 |
| 唯一锚点 | 替换串不唯一就加长上下文，或显式全局替换 | "替换第一处"是静默改错位置，比失败更糟 |
| 精确失败 | 匹配不上就**重读文件**，不要换个模糊写法硬试 | 模糊匹配会改到相似但不相干的代码 |
| 一次一处 | 一个意图一次提交/一次验证 | 失败时能定位到具体改动 |
| 留退路 | 大改前 `git status` 干净、或先备份、或开分支 | 回不去的时候，人会开始"凑合修" |
| 立刻验 | 改完马上跑对应档位，不攒到最后 | 攒到最后一次跑，报错信息会和改动脱节 |

关于批量替换：`sed -i` / 全库替换前，先 `--dry-run` 或先输出命中行数。**改 40 个文件的豪举，配 0 次预演，通常以逐个回滚收场。**

## 六、文档、图、链接同属交付物

- **链接要能被脚本校验。** 用 `verify(checks=["links"])`，别靠肉眼。它就是下面这段的最小实现：

```python
import pathlib, re
for f in pathlib.Path('.').rglob('*.md'):
    for t in re.findall(r"\]\(([^)#]+)\)", f.read_text(encoding="utf-8")):
        if t.startswith(("http", "#")):
            continue
        assert (f.parent / t).exists(), f"{f}: 断链 {t}"
```

- **文档里的代码块要 compile。** 否则"示例"只是长得像代码。用 `verify(checks=["blocks"])`；
  故意不完整的片段（伪代码/片段续写）把围栏写成 `python no-compile` 显式豁免，不要靠"这次就算了"。
- **图要真看，不能只看代码。** 渲染成 PNG 后逐项检查：文字是否溢出方框、元素是否重叠、箭头是否指向正确、边缘是否被裁切、深色/浅色主题下是否可读。文本正确 ≠ 视觉正确 —— 一张图的标注被参考线穿过，只有看图才发现。
- **文档里的常量要插值，不要手写。** 描述里写"上限 200"，代码里 `MAX_ROWS` 改成 500 之后，文档就开始说谎，而且不会报错。

## 七、禁止清单

1. **不编数字。** 没有实测值就写"未测"，不要写一个"看起来合理"的数。
2. **不用"应该可以"当交付。** 那是猜想，不是结论。
3. **不为通过测试改断言**（除非断言本身写错，且必须说明为什么错）。
4. **不在验证不了的环境声称已验证。** 没跑就是没跑。
5. **不在未读文件的情况下改文件。**
6. **不隐藏失败。** 失败的输出原样贴出来，比"已修复"更有价值。
7. **不把"更详细"当成"更好"。** 描述、注释、文档都一样：加了没用的字数，会稀释有用的部分。
8. **测试不碰用户数据目录。** 任何会读写 `~/.app/`、用户工作空间、真实数据库的测试，都必须先隔离（临时目录 + 环境变量 + 独立 workspace）。"跑完再清理"不算隔离——清理的那一刻，你已经在删真实数据了。

## 八、交付前检查清单

直接粘进 PR 模板：

```markdown
- [ ] 语法/导入通过（第 0 档）
- [ ] 本次改动的对应档位验证跑过，**命令与输出已贴出**
- [ ] 新增或改动的数字，有可复现的命令
- [ ] 错误路径的文案有指路（不是只有"失败"）
- [ ] 边界场景想过并验过（空/超大/参差/编码/超时）
- [ ] 涉及结构时，文档、链接、图已同步
- [ ] diff 只包含一个意图（一次一处）
- [ ] 没有临时调试代码、注释掉的旧实现、`print("debug")`
```

## 九、真实复盘（这套规矩怎么来的）

| 差点错的地方 | 怎么抓到的 | 沉淀成哪条 |
|---|---|---|
| 把重写量估成 900 行 | 统计教程里代码块实际行数 → 1500 | 铁律 2、第四节 |
| 记得测试是 5 个脚本 | `ls tests/*.py` → 7 个（期间新增了 `test_sessions.py`，236 行，带多会话功能一起进） | 数字会随仓库漂移，交付前重测 |
| 记忆里 WebUI 端口是 8765 | 读 `webui/server.py` → 8888 | 记忆是最不可靠的来源 |
| 评测本打算写"命中率 85%" | 真跑 20 条 → 15/20 = 75%，13 分 40 秒 | 差 10 个点是另一个结论 |
| 一张时序图的标签被参考线穿过 | 渲染 PNG 才看见 | 第六节：图要真看 |
| 5 个"失败用例"里 3 个其实是合理多步 | 逐条复盘行为，而不是看数字 | **指标也会错，验证要验到指标本身** |
| 用 `max(mtime)` 猜"本次测试生成的文件"然后删除 | 测试实例启动时自动接上了用户最近一次会话，删掉的是他的对话存档 | 禁止清单 8：测试必须隔离，清理只认自己创建的路径 |

最后一条是这套规范的边界：**验证不只是"代码对不对"，还包括"我用来判断对错的尺子对不对"。** 一个把"先找文件再执行"判成错误的指标，会让你把正确的行为改坏。

## 十、想约束我的时候，三句话就够

| 你说 | 我会被迫给出 |
|---|---|
| "证据呢？" | 命令 + 真实输出，而不是"已经改好了" |
| "这个数字哪来的？" | 来源或命令；没有就说"未测" |
| "一次只改一处" | 拆开改动，让每次失败都能归因 |

反过来，如果你只想要快、不在乎证据，直接说"先试一版，不用验证" —— 我会照做，但会标清"未验证"，这个标记不会因为后面聊得投机而消失。
